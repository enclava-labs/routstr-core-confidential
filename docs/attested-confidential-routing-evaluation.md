## Goal

Routstr should be able to run inside a TEE and route only to model backends where confidentiality is verified end to end. For this evaluation, the target backends are:

- Tinfoil
- PPQ private TEE models
- Privatemode

The important security property is fail-closed routing. If a requested model cannot be served through a currently verified confidential path, Routstr must reject the request instead of falling back to a normal plaintext upstream.

## Current Codebase Shape

Routstr is already a good starting point for this because upstream providers and model routing are centralized:

- `routstr/proxy.py` owns the request path: parse model, resolve model object, resolve provider list, charge, then try upstreams in order.
- `routstr/algorithm.py` builds `_model_instances` and `_provider_map` by collecting candidates from all enabled upstreams and sorting by alias priority and cost.
- `routstr/upstream/base.py` owns HTTP forwarding, model-name transforms, streaming handling, and cost metadata injection.
- `routstr/core/db.py` already has `UpstreamProviderRow.provider_settings`, which can carry provider-specific attestation configuration without an immediate schema explosion.
- `routstr/core/admin.py` and the UI already expose provider settings as JSON, but only Routstr-node auto-topup currently consumes it.

The current design is underengineered for verified confidentiality. It treats upstreams as interchangeable OpenAI-compatible HTTP services. That is fine for ordinary routing, but it is not enough for attestation because the router cannot distinguish "this provider can serve the model" from "this provider has a verified confidential transport for this model right now."

### Tinfoil

Tinfoil SDKs are drop-in OpenAI replacements and automatically perform security verification on each connection. Their docs say direct HTTPS access is not recommended for production because manual attestation is required and otherwise there is no cryptographic proof that data is processed in a secure enclave.

Tinfoil verification binds three things:

- expected enclave measurements from GitHub/Sigstore transparency material
- the enclave hardware attestation report
- the enclave-generated TLS and HPKE keys

Tinfoil also supports chained enclaves: a verified router enclave can verify and encrypt to downstream model enclaves.

Integration implication: a plain `BaseUpstreamProvider` pointed at `https://inference.tinfoil.sh/v1` is not sufficient unless the forwarding client uses Tinfoil's verified transport or Routstr reimplements the Tinfoil verification and EHBP flow. Selected Tinfoil model routing is also not satisfied by verifying only the router enclave: preflight and runtime refresh require `require_model_attestations=true`, exact `model_ids`, and `model_attestation_targets` for every selected model so the router proof is chained to the downstream model enclave proof. Routstr passes those exact `model_ids` into the standalone verifier payload, and the Go verifier rejects payload model IDs that do not exactly match the configured model-attestation target keys.

Routstr's default Tinfoil gate is deliberately stricter than Tinfoil's default JavaScript SDK EHBP mode. The SDK docs describe EHBP as the preferred/default transport and TLS pinning as a separate transport mode; EHBP encrypts bodies to the attested HPKE key, while TLS key binding proves the TLS session itself terminates inside the enclave. By default Routstr requires both: the standalone Go verifier rejects `skip_tls_key_binding`, fetches the live TLS public key, verifies it matches the attested TLS key, and separately verifies that the fetched `/.well-known/hpke-keys` public key matches the attested HPKE key before marking a route verified. A live probe on 2026-06-03 showed the Tinfoil router's HPKE key config public key matched the second half of the SNP `report_data`, but the live TLS public-key fingerprint still did not match the first half of `report_data`; under Routstr's default full-channel gate, that remains a blocker. Routstr now also supports an explicit Tinfoil EHBP-only policy mode via `transport_security="ehbp"` or `tinfoil_transport_security="ehbp"`. That mode omits the TLS-binding requirement only when the local provider policy says so, still requires the attested HPKE key to match the fetched EHBP key config, still rejects malformed TLS claims if they are present, and threads the same policy through route-time and public-proof checks. This is a policy-scoped transport choice, not a weakening of the default verifier.

Tinfoil's current audio catalog describes speech-to-text transcription, translation, and audio understanding, so the confidential endpoint contract advertises exact `/v1/audio/transcriptions` and `/v1/audio/translations` support rather than the whole `/v1/audio` family or text-to-speech. Routstr preserves Tinfoil's per-model `endpoints` catalog field and treats it as a ceiling: a model with only chat/audio endpoints cannot inherit provider-wide Responses support, a catalog-only TTS model remains unroutable until Routstr explicitly supports confidential `/v1/audio/speech` for that provider, catalog `tool` services such as `websearch` are not prompt-bearing model routes even when the provider catalog lists chat or Responses endpoints, and malformed endpoint-list entries leave the model with no routable confidential endpoints.

### PPQ Private TEE Models

PPQ private models are OpenAI-shaped, but their docs explicitly say `private/*` models cannot be called directly through `https://api.ppq.ai/v1/chat/completions`. The request body must be HPKE-encrypted against the enclave's attested public key, and PPQ points users to the open-source `ppq-private-mode-proxy`.

The current proxy source starts a loopback OpenAI-compatible API on port 8787 and forwards encrypted chat-completion bodies to `api.ppq.ai/private/v1/chat/completions` with `X-Private-Model` and `x-query-source` headers. Routstr's direct PPQ private path is therefore not the normal PPQ `/v1` API path; it is a from-scratch EHBP implementation of the private proxy's upstream path.

The private model list is discovered by `GET /v1/models?type=all` and filtering IDs beginning with `private/`, so Routstr should not hard-code PPQ private model names. PPQ's current public docs and live catalog snapshot on 2026-06-03 list `private/kimi-k2-6`, `private/gpt-oss-120b`, `private/llama3-3-70b`, `private/qwen3-vl-30b`, `private/glm-5-1`, and `private/gemma4-31b`.

Cross-check against `~/s/p/enclava/confidential-inference` on 2026-06-03: PPQ now has verifier code and model-aware private targets for those six `private/*` models, but the current checked-in attestation results file still has no PPQ rows. Routstr therefore cannot inherit PPQ verification from the directory. PPQ private support is conditional on Routstr's own PPQ Private TEE verifier path, exact `private/*` selectors, PPQ private EHBP key binding, attestation-bundle URL binding to the private origin, a production provenance/release pin, and backend model-enclave attestations matching `model_attestation_targets` for every selected private model. Strict external guardrails also reject PPQ policies until current PPQ result rows exist for every selected `private/*` model, including router release binding, backend release binding, backend TLS binding, backend Sigstore proof, and backend image verification; a host-only `api.ppq.ai` result is not enough for selected-model readiness.

PPQ's Responses API docs also state that `private/*` models are not supported there and should use the Private TEE flow.

Integration implication: the ordinary `PPQAIUpstreamProvider` discovers and forwards normal PPQ models only. `PPQPrivateUpstreamProvider` owns `private/*` models and reimplements the private proxy's EHBP attestation/encryption protocol directly.

### Privatemode

Privatemode is accessed through its own proxy. The proxy is the API endpoint; it verifies `api.privatemode.ai`, performs remote attestation, encrypts prompts, and decrypts responses. The proxy can run as a container, static binary, or Helm chart.

As of Privatemode API docs v1.43, rechecked on 2026-06-03, the proxy supports OpenAI-compatible chat completions, completions, embeddings, models, speech-to-text, and Anthropic-compatible messages.

Routstr treats the Privatemode proxy `/v1/models` `tasks` and `endpoints` fields as model-level capability ceilings: generation/tool-calling models can publish chat, legacy completions, and Anthropic Messages; embedding models publish only `/v1/embeddings`; speech-to-text models publish only `/v1/audio/transcriptions`; unknown task shapes publish no confidential inference endpoints until explicitly audited; and malformed task or endpoint-list entries leave that model with no routable confidential endpoints.

The Privatemode verifier now also binds selected models to workload identities in the attested Contrast manifest. Privatemode policies must use exact `privatemode/*` Routstr model ID selectors, must include `expected_workload_sans` or `expected_workload_ids` as arrays of unique non-empty strings, and must include `model_workload_bindings` entries that map each selected Routstr model ID to those expected workload SANs or IDs. Routstr passes the exact selected `model_ids` into the standalone verifier payload, and the Go verifier rejects payload model IDs that differ from the binding keys. The standalone verifier parses the manifest `Policies` object, requires those workload SANs or workload secret IDs to be present, emits `attested_workload_identity_digest`, `attested_workload_policy_digest`, `expected_workload_identity_digest`, and `model_workload_binding_digest`, and sets `ai_worker_measurement` to the attested workload-policy digest rather than to the generic manifest digest. Runtime refresh, the standalone Go verifier command, verifier-output validation, deployment preflight, route-time proof checks, public metadata validation, and public live checks reject Privatemode `model_id_prefixes`, unprefixed Privatemode model IDs, missing bindings for selected models, bindings for unselected models, scalar or duplicate workload selectors, conflicting workload selector aliases, duplicate normalized model-workload binding keys, conflicting model-workload binding aliases, or binding values outside the configured expected workload set. Runtime refresh, public-proof validation, and the live check also recompute `key_release_binding` from the manifest, mesh CA, secret-service certificate, inference-secret, NVIDIA OCSP MAC, expected workload, and model-workload binding digests, so a copied or malformed key-release digest cannot authorize an unrelated workload proof. This prevents a valid Privatemode manifest proof for one workload from being reused as proof for a different selected model.

Privatemode has important deployment knobs:

- image should be pinned by digest, not `latest`
- the proxy workspace should persist manifest logs for auditability
- `--dumpRequests` must remain disabled
- prompt cache sharing must be off unless Routstr deliberately isolates tenants with cache salts
- NVIDIA OCSP defaults tolerate some uncertainty, so a high-assurance mode should make revocation policy stricter

Privatemode does not encrypt all fields. It leaves routing and billing metadata such as `model`, `stream`, `max_tokens`, `max_completion_tokens`, and `n` visible, and response `id`/`usage` visible.

Cross-check against `~/s/p/enclava/confidential-inference` on 2026-06-03: Privatemode has a single reference-only result row, `privatemode-api`, with status `failed`. The row exposes manifest workload names for operator awareness, but its failure reason explicitly says the public manifest contains reference values only and full verification requires the Privatemode proxy to verify Contrast Coordinator remote attestation and the enforced manifest before encrypting traffic. Routstr therefore treats this directory row as a guardrail and never as route-enabling proof.

Integration implication: use a local Privatemode proxy inside the same trusted deployment boundary as Routstr, and treat its attestation status and manifest log as provider health inputs. Routstr should only publish a selected Privatemode model after the local proxy/verifier has completed the Contrast attestation flow and the policy binds that exact Routstr model ID to attested workload SANs or IDs through `model_workload_bindings`.

## Implemented Foundation

This checkout now has the fail-closed routing foundation and isolated verifier-command boundaries for local and provider attestation.

- `CONFIDENTIAL_ROUTING_MODE=required` makes `_provider_map` and `model_instances` include only aliases whose runtime confidentiality status is currently `enabled=True`, `verified=True`, evidence-backed, and bounded by a future `expires_at`.
- `BaseUpstreamProvider` exposes `ConfidentialityStatus`, `confidentiality_status()`, and `set_confidentiality_status()`.
- `ConfidentialityStatus` now carries verifier identity, policy digest, evidence digest, verified claims, selectors, and freshness. A runtime status must use strict JSON booleans for `enabled=True` and `verified=True`, strict JSON strings for proof identity fields, strict JSON object proof claims, and strict JSON arrays of unique non-empty strings for `model_ids` / `model_id_prefixes`; string booleans, scalar string selectors, numeric selectors, duplicate selectors, tuples, and sets are rejected as proof and truthy strings are not accepted as proof. Verifier identity returned by provider and local Routstr TEE verifier commands must be a real non-empty JSON string, not a number or object coerced into a display label. A runtime `verified=True` status without evidence fields, full `sha256:<64 hex>` policy/evidence digests, a non-empty canonical JSON object in `verified_claims`, or a future `expires_at` is automatically downgraded to unverified. ## Gaps To Close

1. **Local Routstr TEE attestation still needs live deployment validation**

   Routstr now exposes a local attestation statement with configured or freshly generated TEE evidence, evidence format, routing-policy digest, public-key digest, HPKE key-config digest, and local verifier status, serves that key config from `/.well-known/hpke-keys`, and fails model inference requests when local evidence, evidence format, key config, public-key binding, report-data proof claims, or digest-pinned verifier output is absent. `verifiers/routstr-tee-attest-go` can generate nonce-bound SEV-SNP reports and bridge TDX to a pinned QuoteV4 generator; `verifiers/routstr-tee-go` verifies the resulting TDX/SEV-SNP evidence. The remaining gap is live deployment work: run the command inside the target TEE, provide the platform TDX QuoteV4 generator when needed, prove the live Routstr process/key material is what produced the quote, pin both command digests, and validate the whole path against production TEE artifacts.

2. **Provider verifier commands exist, but still need live deployment validation**

   The route policy now filters `_provider_map`, and all three named integrations have distinct provider types. Tinfoil and PPQ private can use the standalone `verifiers/tinfoil-go` binary as a digest-pinned command, and Routstr will only publish verified routing after it sees payload-bound output, required verification-step claims, the configured source repo claim, a required artifact identity pin, any additional configured digest-shaped measurements, and an HPKE key bound to the fetched EHBP key config. For Tinfoil that identity pin must be an exact release digest; PPQ private can use a release digest or digest-shaped code-measurement fingerprint with its configured attestation bundle. Public/live verification also requires the Tinfoil router policy repo/release pins, each selected Tinfoil model target's repo/artifact pins, and PPQ private's public attestation-bundle URL digest plus release or code-measurement pin before treating provider proof as bound to local policy. Privatemode can use the standalone `verifiers/privatemode-go` binary as a digest-pinned command, and Routstr will only publish verified routing after it sees payload-bound output, required verification-step claims, matching manifest/proxy artifact claims, Coordinator, secret-service, AI-worker, GPU policy, key-release claims, attested workload identity/policy digests bound to the configured expected workload selectors, and a model-workload binding digest for exact selected model IDs. The remaining gap is not command scaffolding; it is live validation against the exact providers and deployment artifacts intended for production.

3. **Provider-specific evidence still needs live E2E validation**

   Runtime provider instances now expose freshness, model selectors, verifier identity, policy digest, evidence digest, verified claims, refresh hooks, and operator-facing failure reasons. Tinfoil-compatible hardware/Sigstore/EHBP checks and Privatemode Contrast/manifest/secret-exchange checks now have real command implementations, but they still need live-provider E2E verification in the target deployment.

4. **Alias collision is covered for required mode, but namespaces are still preferable**

   The algorithm deliberately maps many aliases for convenience. In required confidential mode, provider selection and the selected `Model` metadata now both come from verified confidential candidates when a normal and confidential provider share an unqualified alias such as `gpt-oss-120b`. Exact `model_ids` selectors apply to the route alias being published, so selecting `tinfoil/gpt-secure` does not implicitly publish `gpt-secure`, selecting `gpt-secure` does not implicitly publish `tinfoil/gpt-secure`, and PPQ private requires exact `private/<model>` selectors rather than a broad `private/` prefix. Explicit namespaces are still preferable operationally because they make confidentiality expectations visible to clients.

5. **PPQ private integration needs production provenance pinning**

   `PPQAIUpstreamProvider` no longer exposes `private/*`, and `PPQPrivateUpstreamProvider` owns private-model discovery. Routstr now probes PPQ private EHBP keys, calls the Tinfoil-compatible verifier command, binds that result to the HPKE key and attestation-bundle URL, and encrypts prompt-bearing requests directly. The current live PPQ private endpoint verifies with Tinfoil `confidential-model-router` provenance and release digest `sha256:ebb921d8572bc8f6b4e04812a7e65bffcf6ac1a2fabe8a55115a13d61e901b85`. The remaining deployment gap is to decide whether that is the exact production identity to pin, or whether PPQ will publish a PPQ-owned repo/provenance identity for the private endpoint before rollout.

6. **Logging/error paths still need live sidecar and manifest-log review**

   Core upstream error paths now redact protected-route body previews, and verifier subprocess failures expose only stderr byte counts plus digests instead of raw stderr. Real deployments still need review around live sidecar logs, Privatemode manifest-log retention, provider SDK debug hooks, and operator log collection paths.

7. **Verification still needs live evidence coverage**

   The foundation has tests for fail-closed routing, the verifier refresh lifecycle, model-list confidentiality metadata, verifier-command contracts, and the standalone Go verifier build/test path through preflight. Remaining validation should cover live manifest/evidence failures, provider-specific protected-route diagnostics against real providers, and a real end-to-end confidential request inside the target TEE deployment.

## Recommended Architecture

### 0. Define "From Scratch" Verification

There are two possible integration levels:

- **Sidecar-verified**: Routstr runs a provider's open-source local proxy/SDK inside the same trusted boundary and only routes after that proxy reports verified status. This is the fastest production path for PPQ and Privatemode because their public docs present local proxies as the supported API surface.
- **Routstr-verified**: Routstr itself validates the hardware evidence, transparency/provenance material, key binding, revocation state, and provider policy before encrypting any request. This is the stricter interpretation of "verify everything from scratch."

The requested end state should target Routstr-verified. Sidecar-verified is acceptable as an interim milestone only if the sidecar image/binary is pinned, audited, included in the Routstr TEE measurement/attestation policy, and prevented from dumping plaintext.

Provider-specific verifier scope:

- **Tinfoil**: verify the remote attestation document, hardware signature chain, expected measurements from GitHub/Sigstore transparency material, certificate SAN binding, HPKE public key binding, freshness, and TLS public key binding unless the policy explicitly selects EHBP-only transport before sending encrypted request bodies.
- **PPQ private TEE**: verify the same Tinfoil/EHBP-style enclave evidence for the `private/*` path, plus PPQ routing/billing metadata constraints. The existing PPQ local proxy can guide implementation, but a from-scratch verifier should not blindly trust proxy stdout.
- **Privatemode**: verify the Contrast manifest, Coordinator attestation, manifest equality, Mesh CA handoff, secret-service TLS chain, AI-worker attestation, NVIDIA GPU attestation/OCSP policy, key-release path, and manifest transparency log before upload of encryption keys or prompts.

### 1. Add a Confidential Provider Contract

Add runtime provider capability methods on `BaseUpstreamProvider`:

```python
class ConfidentialityStatus(BaseModel):
    enabled: bool
    verified: bool
    mode: Literal["none", "tinfoil", "ppq-private-tee", "privatemode"]
    verified_at: int | None
    expires_at: int | None
    verifier: str | None
    policy_digest: str | None
    evidence_digest: str | None
    verified_claims: dict[str, object]
    failure_reason: str | None
    model_ids: list[str]
    model_id_prefixes: list[str]

class BaseUpstreamProvider:
    async def refresh_confidentiality_status(self) -> ConfidentialityStatus: ...
    def confidentiality_status(self) -> ConfidentialityStatus: ...
```

Default providers return `enabled=False`.

### 2. Add Route Policy

Add a global setting and per-provider/per-model settings:

- `CONFIDENTIAL_ROUTING_MODE=disabled|prefer|required`
- provider `provider_settings.confidential_transport`
- provider `provider_settings.allowed_measurements` or provider-specific policy
- model `confidential_only` and `confidential_aliases`

For this user's intended deployment, use `required`.

### 3. Filter Before Routing

`refresh_model_maps()` refreshes provider confidentiality status before publishing route maps, and `create_model_mappings()` applies confidential policy before `_provider_map` or `_model_instances` are published. If a provider is not verified, it does not appear in the provider list for confidential aliases; if no verified provider remains for an alias, or if the verified provider/model pair has no endpoint Routstr can serve, that alias is omitted from `_provider_map` and `_model_instances` entirely.

Also add a second lookup path for clarity:

- `get_provider_for_model(model_id)` for normal routing
- `get_confidential_provider_for_model(model_id)` or a policy-aware `get_providers_for_model(model_id, policy)`

The request path should reject with a clear `503 confidential_route_unavailable` or `424 attestation_required` before charging if no verified provider exists.

In required confidential-routing mode, runtime readiness also rejects a static `ROUTSTR_TEE_ATTESTATION_DOCUMENT_PATH` unless a live attestation command is configured, so fixture/offline evidence cannot satisfy the pre-billing gate. For live deployments, the attestation command receives a `routstr-tee-attestation-request-v1` payload containing the routing policy digest, verifier challenge, public-key digest, HPKE key-config digest, HPKE public-key digest, `tee_report_data_digest`, and exact `tee_report_data_hex` value to place into the TDX/SEV report data field. `verifiers/routstr-tee-attest-go` implements this contract for SEV-SNP via `/dev/sev-guest`; for TDX, it requires a digest-pinned external QuoteV4 generator because TDREPORT0 is not the remotely verifiable evidence consumed by the verifier. The attestation command returns a payload-bound `routstr-tee-attestation-document-v1` document. The verifier then receives the routing policy digest, attestation document, attestation document format, public key material, HPKE key config, verifier policy, the same fresh nonce, the recomputed `tee_report_data_digest`, and the same `tee_report_data_hex` field on stdin. `tee_report_data_hex` is a 64-byte SHA-512 value over the canonical `routstr-tee-report-data-v1` binding for the verifier challenge, routing policy digest, configured public-key digest, HPKE key-config digest, and HPKE public-key digest. The verifier must return `verified=true`, verifier identity, matching payload binding values including `attestation_document_format`, required verification steps, a `public_key_digest` matching Routstr's configured public key, non-empty `tee_attestation_report_digest` and `tee_certificate_chain_digest` claims, matching `tee_report_data_hex` and `tee_report_data_digest` claims, a `routstr_code_measurement` claim matching `expected_routstr_code_measurement` or `allowed_routstr_code_measurements` from `ROUTSTR_TEE_VERIFIER_POLICY_JSON`, and a `routstr_config_measurement` claim equal to the current routing-policy digest. Local TEE verification rejects future-dated `verified_at` values and uses the same expiry cap as provider verifiers: explicit `expires_at` values cannot extend acceptance beyond `verified_at + max_verifier_age_seconds` (300 seconds by default). `verifiers/routstr-tee-go` implements this verifier contract for TDX/SEV-SNP-style documents using `tinfoil-go`.

The minimum binding should include:

- Routstr image digest / code measurement
- config digest for confidential routing policy
- TLS public key fingerprint
- HPKE public key if application-layer encryption is used
- public provider policy digest
- build/provenance evidence

If this runs on Enclava/CAP, this should integrate with the existing attestation-proxy/KBS policy path rather than inventing a second trust root.

## Verdict

The provider/routing structure is just right for this feature: the model map, provider adapters, and per-provider settings can carry a clean fail-closed policy layer without a broad rewrite. The original confidentiality model was underengineered for the target state; the implementation now has first-class runtime attestation status, fail-closed provider selection, local Routstr TEE gating, and encrypted EHBP forwarding. The remaining work is deployment-specific live validation, not another routing abstraction.

The pragmatic path is not to rewrite Routstr. Keep the current proxy and billing pipeline, but add a small verified-routing layer in front of provider selection and implement the three confidential providers as explicit provider types. That keeps maintenance cost low while making the confidentiality guarantee visible and testable.
